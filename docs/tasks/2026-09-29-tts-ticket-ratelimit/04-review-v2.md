## 可优化项（合并去重，按价值排序）

1. **当前句长时间限流等待时，预取句手里的票会过期，Chromium 上会不提示地跳过这一句**（并发视角）
   - **位置**：
     - frontend/app/page.tsx:886-895（tryPrefetch）；
     - :941-970（playNextInQueue 把预取句转为当前句时不看票龄）；
     - :918（error 事件走 finishCurrentTts，直接跳句）；
     - backend/routers/voice.py:32（TTS_TICKET_TTL_SECONDS = 60），:132-135（票过期返回 404），:448（Cache-Control: no-store）。
   - **现象**：C6 在 Chromium 上跑 2 次都复现，ended 顺序都是 [1,3,4,5]。第 2 句约在 67s 开始 playing，170–240ms 后触发 error，界面没有任何提示。对照 C6b（票龄约 55.9s）是 5/5；WebKit 跑 C6 一次也是 5/5，可能是它在 load 时已经缓冲了整段短音频。
   - **原因**：后端票据 60s 过期；Chromium 在 no-store 下开始播放时会再请求一次 /tts/stream，拿到 404，触发 error，于是跳过这一句。
   - **真实情形**：当前句被拒、预取句被放行，而且当前句等待加播放的时间超过「60s 减去预取票已过的时间」。最可能出现在用户字数闸快用完时：长的当前句被拒，短的预取句能过，retry_after 最长可到 60s。并发视角认为概率低。
   - **建议**（要先改规格，因为 v2 白名单只有 page.tsx）：
     - (a) 预取句转为当前句时，如果票已签发超过约 45s，就放弃这张票、把文本放回队头重新换票；这需要在 PreparedTtsAudio 里记录签发时刻。
     - (b) 当前句进入限流等待而预取句已持有票时，直接放弃预取。
     - (c) 后端把票据有效期放宽到「最长等待 60s + 一句最长播放时长」以上，例如 150s。
     - 与第 5 项的「FIFO 淘汰导致 404 跳句」是同一类后果，可以一起处理。

2. **补回归测试：仓库测试挡不住「全有或全无」和 Retry-After 取值规则的回归**（后端 + 规格视角合并）
   - **位置**：backend/tests/test_tts_ticket_rate_limit.py；对应 backend/rate_limit.py:46-63。
   - **证据**：M1/R_SEQ（逐项 test→hit）、M2/R_MIN（max 改 min）、M3（只取第一项不通过的 reset）、R_NOFLOOR（去掉下限 1）、R_LASTREJECT（日志改取最后一项不通过）、V_DROP_IPCHARS（整条去掉 IP 字数闸），跑仓库测试都是 14 passed。现有用例只覆盖「第一道闸就拒绝」和「每次只有一道闸不通过、窗口刚开始」这两种情况。
   - **建议**（在下一轮允许改后端测试时做）：
     - (a) 让后面的闸（用户字数、IP 次数或 IP 字数）拒绝，断言前面各闸的余量不变。可以仿照 E1/E1b，或规格视角的对照：用户字数调到 300/minute、第二张 300 字票被拒后，用户次数余量应为 119。
     - (b) 调低 TTS_TICKET_IP_CHARS，同一 X-Real-IP 下多个用户换长票，达到上限后被拒，换一个 IP 仍能通过；T3.6 里也先断言首张票确实扣了 IP 字数。
     - (c) 构造两道闸同时不通过、reset 不同的情况，断言 Retry-After 取较晚的那个，日志的 scope/kind 取第一项。
     - (d) 构造窗口即将到期的情况，断言 Retry-After 不小于 1。

3. **IP 闸依赖反代覆盖 X-Real-IP，但桌面包用的 API 域名在仓库里没有反代配置**（后端视角）
   - **位置**：backend/rate_limit.py:26-28；frontend/lib/config.ts:5；docs/DEPLOYMENT.md:226-243。
   - **风险**：如果 api.madchloechat.online 那一层没有写 `proxy_set_header X-Real-IP $remote_addr`，每次换一个 X-Real-IP 就能绕过 IP 闸，而 IP 闸正是防多账号的那道。用户闸不受影响。这是既有前提，其他 slowapi 限流也依赖它。
   - **建议**：在 DEPLOYMENT.md 补上 api.* 域名的 server block，或写明所有入口都必须覆盖 X-Real-IP。本任务不需要改代码。

4. **规格 1.2/1.3 的费用上限结论漏了三个前提，绝对值低估约 4–8 倍**（后端视角）
   - **位置**：02-spec.md:59、74、76；backend/routers/voice.py:38、465-475、484-492；backend/tts.py:117；backend/tts_ws.py:20-23。
   - **三个前提**：
     - TTS_MAX_TICKET_USES=4。没缓存成功的票每用一次就重新合成一次（E3）；合成线程不会随请求取消，所以可能每次都计费。
     - 固定窗口跨界时可拿到 2 倍额度（E12）。
     - /tts/ws 完全没挂限流，前端也没在用。
   - **合起来**：单个账号经换票在任意 60 秒内最多约 16000 字，/tts/ws 没有上限。若 DashScope 按 2 个字符计一个汉字，所有绝对值还要再翻倍（未联网核实）。
   - **建议**：
     - 本轮不改代码，把规格表述改为「按换票计的字数额度；每张票最多 4 次合成；固定窗口跨界可到 2 倍；/tts/ws 不受此限」。
     - 后续单列任务：把字数计在实际合成上，或者只允许缓存命中时复用票据；给 /tts/ws 挂同一套闸，或者下线这个端点。

5. **IP 次数闸比今天宽 12 倍，全局 2048 张待用票按 FIFO 淘汰，可能挤掉别人的预取票**（后端视角）
   - **位置**：backend/routers/voice.py:36、39、316-318。
   - **证据**：旧规则每 IP 20 次/分钟，新规则每 IP 240 次/分钟。要让表里常驻 2048 张活票，旧规则需要约 100 个 IP；新规则按持续速率约需 17 个账号、约 9 个 IP，利用跨窗突发约 9 个账号。被淘汰的可能正是别人的预取票，对方拿到 404 就按非 429 失败跳句。每 IP 最多 240×4 次上游合成调用/分钟，可能撞到 DashScope 的并发或 QPS 限制（未核实）。
   - **建议**：在规格或报告里写明这个取舍。以后如果要收紧，可以按用户限制手里的活票数，或者把全局 FIFO 淘汰改成按用户配额。

6. **退避到点时，当前句与预取句同时醒来，请求先后不定**（自动播放 + 规格视角合并）
   - **位置**：frontend/lib/ttsTicket.ts:40-81（v1 文件，不在 v2 白名单内）。
   - **证据**：S9 Chromium 第 1 轮、S10 Chromium、S1 WebKit 都是预取句先发请求；S9 WebKit 和 S9 Chromium 第 2 轮则是当前句在前。播放顺序始终正确。
   - **风险**：窗口里只剩 1 个名额时，当前句可能再吃一次 429、再等一整个窗口（最长 60s）。这会让第 1 项的丢句更容易发生。两个视角都认为默认限额下很少触发，本次没有用真实限流复现。
   - **建议**：非当前句醒来后先让一拍（检查归属，或错开几十毫秒），或按入队顺序串行发请求。也可以保持现状，作为已知限制记下来。

7. **速率模型的前提：385 字/分钟不是上限，「约 15 个用户」只对长段落成立**（后端视角）
   - **位置**：02-spec.md:42-43、77；rate_model.py:10。
   - **证据**：
     - 模型自带样本 (27 字, 3.736 秒) 折合 434 字/分钟，高于「最多约 385」。
     - 拟合只用了 8 句中文。
     - 用 rate_model 复算：碎句（「嗯。」×300）峰值 114 张/分钟，短项编号列表 106–110 张/分钟，离 120 只剩 5–12%。
     - 这种内容下同一出口约 3.5–5 个用户同时朗读就会碰到 IP 次数闸。后果只是等待，不会跳句。
   - **建议**：把 385 标成拟合均值，注明模型只覆盖中文；把「约 15 个用户」改为按内容区分：长段落约 15 个，碎句或列表约 4–5 个。数值不用改。

10. **验收 harness 有几处指标容易误读**（自动播放 + 规格视角合并，不是被测代码的问题）
