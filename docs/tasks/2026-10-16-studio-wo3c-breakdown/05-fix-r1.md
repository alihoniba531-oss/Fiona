## 二、另外一并处理 04-review.md §3 的以下可优化项（作者同意一起修）
- **O1 轮询写放大**：`get_current` 不得每次 GET 都全量 DELETE/INSERT 单元、重写总表和 `import_json`。只有某批的 job 状态与 chunk 状态不一致，或者拆解处于 `running / partial` 且有新完成的批时，才做物化；`done / cancelled` 且没有差异时直接读表。补测试：连续两次 GET 不产生任何写入（可统计 `total_changes`）。
- **O2 收回越界改动**：撤回 `store._one / _many` 全局 `to_thread` 的改动，恢复成 WO3b 时的写法，只在拆解模块对大 JSON 列做线程化解析。
- **O3 报价不存全书正文**：`studio_quotes.items_json` 只存章号、块号、偏移和估算值，不存正文；`start()` 时按 `snapshot_no` 重读快照来组装输入（快照号不一致就 409）。`studio_chunks.source_json` 也不要再保存一份 `_inputs` 全文，组装输入在执行时按需读快照。补测试：报价行的 JSON 大小不随正文长度线性增长。
- **O4 锚点未命中的回退**：未命中那一场的 `start` 取「下一个命中锚点的位置」，没有则取块末。命中的场保住自己的原文；未命中的场可以为空，并带 warning。更新相应测试。
- **O5 warning 归属**：`locate_scenes / merge_bible` 的 warning 写回来源批（或在拆解级别单列并标明来源批），不要全挂在第 1 批上。
- **O6 防止作者修改被静默覆盖**：拆解处于 `running / partial` 时：
  - 分集表上方显示「拆解尚未全部完成，补跑完成后分集方案会按新结果重新生成」。
  - 操作菜单与「批准」禁用，并给出原因。
  - 后端 ops 接口在这两种状态下返回 409。
- **O7 重新拆解期间保留旧方案**：新拆解完成并发布方案之前，分集表和 G0 状态继续显示上一份已发布的方案，并标注「新的拆解进行中，完成后会替换此方案」。新方案发布时 revision 加 1，自然变为待批准。不得出现「0 集但显示已批准」。补测试。
- **O9 恢复不阻断启动**：`recover()` 逐个拆解 try/except 并记日志，任何一个出错都不能让 `recover_studio_jobs` 抛出。补测试。
- **O11 报价时会保存时长**：报价对话框里明确提示「每集目标时长将保存为 x–y 秒」。如果这次保存会让已有分集方案的 revision 加 1，要提示「会使已批准的分集方案变为待批准」。
