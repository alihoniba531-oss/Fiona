# 简报：修改意见卡（分身把修改意见交给书斋）

日期：2026-11-12。基线：Fiona `main` = `7a17f64`。

## 1. 作者的原话与场景

作者在主聊天里用自带的 Claude 和分身讨论自己在书斋里写的长篇。分身读完原文，写出了一份很具体的修改意见（时间线矛盾、某章偏离大纲、某人物不能提前退场等），作者说「你来告诉写手，把偏离的部分修改正确」。分身回答：它手上的工具只能列书、读原文、建草稿，没法跟书斋的写手说话，只能请作者在确认细纲那一步自己把意见贴过去。

作者问「是否可以增加交互功能」。我提出分两步做：第一步让分身把意见做成卡片，作者点一下就交给书斋；第二步让书斋能按意见重写已经写好的章节（要先给章节正文加历史版本和撤销）。作者回复「好的，着手帮我解决这个交互的问题」，即按建议先做第一步。

## 2. 调查结论（七路只读调查 + 交叉核对，规格作者已亲自复核关键行号）

### 2.1 书斋接收作者意见只有三个入口，各有局限

| 入口 | 位置 | 生效范围 | 费用 | 局限 |
|---|---|---|---|---|
| 给编辑部留言 | `POST /novels/{id}/notes`，`service.note()`（`novel/service.py:642-649`） | **只在某一章第一次规划细纲时被读一次**（`runner.py:314`、`:347-350`），这一章写完归档时标为已下发（`store_db.py:320-329`），之后不再出现 | 免费 | 1–500 字；每本书待处理最多 5 条；没有撤回、编辑接口；接口不返回留言 id、不幂等 |
| 带一句话重做细纲 | `POST /novels/{id}/plan/redo`，`service.redo_plan()`（`:449-461`） | 只对正在等确认的那一章（取章号最大的 `awaiting_plan_approval`，不能指定章号） | 每次都调用一次主编并计费（`runner.py:492` 步骤键含 `redo{n}`） | 只在 `awaiting_plan` 状态可用；1–500 字；附言以 `author_instruction` 字段交给主编，主编提示里没有专门说明这个字段 |
| 作者自己改正文 | 书斋「改稿」→ `PUT /novels/{id}/chapters/{n}` | 只改这一章正文 | 改最新章会触发付费的重新归档；改较早的章免费 | 没有历史版本和撤回；改较早的章会把后面已写的章永久标为「待复核」，有待复核章的书不能再做成片（`studio/sources.py:65-66`） |

### 2.2 「等确认细纲」时留言管不到当前这一章

逐章确认（`per_chapter`）的书每写完一章都会停在「等你确认细纲」。这时第 N 章的细纲已经出来了：新留言不会进入第 N 章（批准后直接按存档细纲写正文，重做也只用当初那份简报里的留言），要到第 N+1 章规划细纲时才会被读到。想让第 N 章照意见改，只能重做细纲，或作者自己改细纲再批准（后者免费）。

### 2.3 书斋没有「按意见改已写章节」的流程

主编规划细纲时看不到任何章节正文，只看摘要和时间线。如果留言写「把第 3 章重写成某某」，主编只能裁决眼前这一章，可能标「采纳」却什么也没改，也可能把没发生的改动当成事实写进后面的细纲。这正是第二步要解决的问题，第一步只能如实告诉作者「已写章节不会自动修改」，并给出手改入口和风险提示。

### 2.4 聊天侧

- Claude 智能体的小说工具按开关逐轮追加（`services/claude_agent.py:85-110`），模型只知道书名，不知道书的 id；按书名找书复用 `studio/novel_chat.py:34-45` 的 `_resolve`。
- 聊天侧五个文件被 AST 锁限定只能导入书斋的只读函数（`backend/tests/test_studio_sources_readonly_integration.py:177-208`），所以「交给编辑部」「重做细纲」必须由作者点卡片后，经书斋的 HTTP 接口完成。
- 先例「聊天建书」：`draft_novel` 工具 + `novel_drafts` 表 + `messages.novel_draft_id` + `NovelDraftCard`。本功能沿用同一套路。

## 3. 方向

做一张「修改意见卡」。分身把意见按用途分成三类写进卡片，作者在卡片上逐项决定：

1. **以后的章节**：点「交给编辑部」，成为一条留言（免费，交出后不能撤回）。卡片写明它只在下一次规划细纲时参考一次；等确认第 N 章细纲时交出的，要到第 N+1 章才看到。交出后卡片显示编辑部用在哪一章、回应了什么。
2. **第 N 章细纲**（只在这本书正等确认第 N 章细纲时）：点「带着这些要求重做细纲」，确认框说明会扣费，作者确认后才发起。卡片记住章号，书已经不在等确认第 N 章时按钮失效，不会把第 N 章的意见用到第 N+1 章。
3. **已写好的章节**：只列出问题，提示作者去书斋「改稿」，并说明改较早章节的后果。

## 4. 风险

- 留言是一次性的，「以后每章都要……」这类长期约束目前没有通道；卡片文案要如实说明。
- 重做细纲的附言在主编提示里没有专门说明（现有行为，书斋里手动重做也一样），效果靠模型理解。
- 分身写的意见可能超过 500 字；工具要求分身精简，不静默截断。
- 卡片状态（交没交、重没重）下一轮模型看不到；工具结果里写明「要等作者点按钮」，避免分身声称已经交了。
- 作者的试用库只有一本书、一条留言、从未重做过，多本书、留言满 5 条、已下发回应等情形靠测试夹具覆盖。
