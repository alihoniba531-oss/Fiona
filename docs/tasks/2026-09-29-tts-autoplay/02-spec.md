## 1. 背景：现在为什么会整段静默

朗读队列在 `frontend/app/page.tsx` 的 `mkTtsAudio` / `tryPrefetch` / `playNextInQueue` / `clearTtsQueue`（大约 730–890 行）。现在的做法：

1. 每一句都 `new Audio()` 一个新元素。
2. 先 `POST /tts/ticket` 换一张票，拿到后 `audio.src = /tts/stream?ticket=…`。
3. 然后 `audio.play().catch(onDone)`。

WebKit 内核（macOS Safari、iOS 上所有浏览器、macOS 的 WKWebView）对**每个媒体元素**单独要求：这个元素第一次 `play()` 必须发生在用户手势里。第 2 步是异步的，`play()` 调用时早已不在手势里了，而且每句都是没被手势碰过的新元素。结果是 `play()` 被拒（`NotAllowedError`），`catch(onDone)` 把它当作「这句放完了」，于是跳到下一句，下一句同样被拒……整段回复一声不出，界面上也没有任何提示。

实测证据：无头 WebKit 跑 5 次，其中 1 次 5 句全部被拒（`NotAllowedError` ×5）。首字越慢越容易触发，iOS 真机更严格。Chromium 和 WebView2 是「整页有过交互就放行」，所以不受影响。

## 2. 目标

1. 用户在本页通过手势打开朗读后（点「朗读」、点「免提」、点气泡里的「帮我读」都算），本页之后的所有朗读在 WebKit 下都能正常出声。包括：
   - 首字很慢的回复；
   - 免提模式下没有手势、自动发出去的消息。
2. 万一浏览器仍然拒绝播放，不再静默跳过：
   - 朗读停在被拒的那一句；
   - 输入区上方出现一行提示和「点此播放」按钮；
   - 用户点击后，从这一句开始继续往下读，不丢句。
3. Chromium/WebView2 的行为和现在一致：句间预取、没有空档，首音延迟不变差。

## 3. 设计要求

### 3.1 两个可复用的 audio 元素

- **元素池**：页面持有**恰好两个**长期存在的 `HTMLAudioElement`。
  - 第一次需要时创建，存在 ref 里，组件生命周期内不重建，`preload = "auto"`。
  - 「当前句」和「预取的下一句」轮流使用这两个元素。
  - 不再每句 `new Audio()`。
- **归属**：
  - 同一时刻，一个元素最多只属于一句（当前句或预取句）。
  - 一句结束后（播完、出错、被放弃、被清空），元素才回到池里。
- **身份判断**：因为元素会被复用，**不能再用元素本身来判断「是不是还是这一句」**。
  - 现在的 `ttsAudioRef.current !== audio` 这类判断，要改为按「每句一个播放对象」判断，例如 `PreparedTtsAudio` 对象本身。
- **监听清理**：
  - 挂在元素上的这一句的监听（`ended`、`error` 等），在这一句结束时必须**全部移除**，例如用 `addEventListener` 的 `signal` 选项配合 `AbortController`。
  - 不能只靠 `{ once: true }`：`ended` 触发后 `error` 监听还挂着，下一句复用这个元素时，会误触发上一句的回调。
- **监听生效时机**：一句的 `ended` / `error` 监听，只有在把它的票据地址设为 `src` 之后才生效。在此之前，这个元素上发生的任何事件都不能影响这一句，包括：
  - 3.2 静音解锁音频的 `ended`；
  - 移除 `src` 时产生的 `error` / `emptied` / `abort`。
- **接手元素**：一句接手元素时，如果元素上还在放静音解锁音频，先停掉它（pause，移除 `src`）。
- **迟到结果保护**：迟到的异步结果不能写入已经换了主人的元素。换票请求返回之后，设置 `src`、调用 `load()`、`play()` 之前，都要确认三件事：
  - 这一句仍然拥有这个元素；
  - 这一句没有被取消；
  - 会话号（`ttsSessionRef`）没有变。
- **`clearTtsQueue`**：语义不变，仍然是停止当前句和预取句、中止换票请求、清空队列。区别是：对池里的元素只做「pause + 移除 `src` + `load()`」然后放回池里，而不是丢掉。

### 3.2 在用户手势里解锁元素

- **解锁函数**：提供一个**同步**的解锁函数，例如 `primeTtsAudio()`。它只处理池里「空闲且还没解锁」的元素，对每个这样的元素：
  - 设置一段很短的静音音频（几十毫秒的 WAV）。
    - 在代码里生成，或者内联一个短 data URI。
    - 不新增二进制文件。
    - CSP 已经允许 `media-src data: blob:`。
  - 调用 `play()`。
- **调用时机**：解锁必须在用户手势事件处理函数的**同步部分**里调用，也就是任何 `await` 之前，否则 WebKit 不认。
- **怎么判断解锁成功**：
  - `play()` 被拒且 `error.name === "NotAllowedError"`：这个元素仍算没解锁，下次手势再试。
  - 其他情况：算作已解锁，以后不再对它放静音。包括：
    - `play()` 成功；
    - 因为随后被换源或暂停而得到 `AbortError` 等其他错误。
  - 无论成功还是失败，事后如果这个元素仍然空闲、仍然是这段静音源，就 pause 并移除 `src` + `load()`。如果它已经被真实句子占用（`src` 已换），就不要碰它。
- **不打扰正在用的元素**：静音解锁不能作用于正被某一句占用的元素。不能打断当前句，也不能提前播放预取好的句子。
- **必须同步调用解锁的手势**：
  1. 点「朗读」按钮，且这次是打开；
  2. 点「免提」按钮，且这次是打开；
  3. 点气泡里的「帮我读」；
  4. 点「点此播放」（见 3.3）。
- **兜底监听**：
  - 在 `document` 上用捕获阶段监听 `click`、`keydown`、`touchend`。
  - 只有当朗读已开启、并且池里还有没解锁的元素时，才调用解锁。
  - 组件卸载时移除这些监听。
- **朗读关闭时不放静音**：朗读关着的时候，任何点击都不能触发静音播放。在 iOS 上，播放音频会打断用户正在听的音乐。

### 3.3 被拒时的提示与续播

- **当前句 `play()` 被拒、且 `error.name === "NotAllowedError"` 时**：
  - 不执行「这一句结束」的推进逻辑，不跳到下一句。
  - 这一句和它的元素、预取句、队列全部保留。
  - 朗读仍然处于「占用中」：新到的句子照常入队和预取，不会另外开始播放。
  - 显示提示，由 React 状态驱动。
- **其他情况**：保持现有行为，跳过这一句、继续下一句。包括：
  - 其他类型的拒绝，比如 `AbortError`、`NotSupportedError`；
  - 元素上的 `error` 事件。
- **提示界面**：
  - **位置**：底部输入区 `footer` 里 `[data-chat-composer]` 容器的顶部，和 `referenceUploadError` 处在同一层级。
  - **内容**：一行。左边文字「浏览器拦下了自动朗读」，右边两个按钮：「点此播放」（带 `Volume2` 图标）和「不听了」。
  - **样式**：
    - 按钮沿用气泡里「帮我读 / 不用」的写法 `btn btn-quiet h-7 px-2.5 text-xs`。
    - 手机宽度下按钮高度改为 36px（`max-md:h-9`）。
    - 文字用 `text-xs text-muted-foreground`。
    - 只用 Tailwind 工具类。不新增颜色、渐变、阴影或大圆角卡片，不改 `globals.css`。
    - 390px 宽的手机上要放得下一行；实在放不下时允许文字换行，但按钮不能被挤出屏幕。
  - **无障碍**：容器加 `role="status"` 和 `aria-live="polite"`；两个按钮都是真正的 `<button type="button">`。
  - **焦点**：不自动抢焦点，不打断用户正在打字的输入框。
- **「点此播放」**：在点击处理函数里按顺序**同步**执行：
  1. 如果预取句占着另一个**还没解锁**的元素：放弃这个预取，包括中止它的换票、释放元素、把它的文本放回队头。
  2. 调用解锁函数，解锁空闲的元素。
  3. 对被拒那一句的元素直接调用 `play()`。不重新换票，也不重新 `load()`。
  4. 隐藏提示。
  5. 如果再次得到 `NotAllowedError`：重新显示提示。不自动重试，不循环。
  6. 如果播放成功：这一句 `ended` 之后照常推进到下一句，优先使用已预取的。
- **「不听了」**：效果等同 `clearTtsQueue()`，停止这次朗读、清空队列，并隐藏提示。**不**关闭「朗读」开关。
- **隐藏提示的时机**：任何一次 `clearTtsQueue()` 都要隐藏提示，包括新发送、切换会话、切换账号、页面卸载。
- **关闭「朗读」开关**：调用 `clearTtsQueue()`，立刻停止当前朗读并隐藏提示。现在的行为是关掉后仍会把已经排队的句子读完，本任务一并改为立刻停止。
- **免提模式**：被拒期间不启动免提录音。队列没读完，自然不会进入「读完 → 开始录音」的分支。续播读完后，照常进入免提录音。

### 3.4 必须保持不变的东西

- **票据流程和隐私**：原文只出现在 `POST /tts/ticket` 的请求体里，`<audio>` 只使用 `/tts/stream?ticket=…`。请求体字段不变：`text` 截到 300 字，`voice`、`speech_rate` 照旧。
- **预取**：当前句播放时，预取队头的下一句，保证句间没有空档。
- **会话号**：`ttsSessionRef` 的失效语义不变。
- **其他逻辑**：以下行为都不变：
  - `normalizeForTTS`；
  - 切句逻辑；
  - `enqueueSpeech` 的 `voiceOn` 守卫；
  - `handleConfirmTts`（帮我读）自动打开朗读。
- **布局**：桌面宽度和手机宽度下，除了新增的提示行，其他布局没有任何变化。

### 5.2 Claude 在浏览器里实测（供你实现时对照，你不用跑）

测试环境：无头 WebKit 和 Chromium，假模型每条回复 5 句，假 TTS 每句约 1 秒。

- **A（WebKit）**：点「朗读」后，发送一条首字延迟 5 秒的消息。5 句全部 `ended`，`NotAllowedError` 为 0 次。同样的场景在基线 `8c7f0cf` 上会被拒。
- **B（WebKit）**：把第一次真实播放模拟为 `NotAllowedError`。
  - 1 秒内出现提示；
  - 点「点此播放」后，5 句按顺序全部 `ended`，没有跳句；
  - 提示消失。
- **C**：在提示出现时点「不听了」。之后没有任何播放，提示消失，朗读开关仍然开着。
- **D**：连续两轮对话，并在播放中途发送一条新消息打断。
  - 任何时刻最多只有一个元素在播放真实语音；
  - 被打断的旧回复不再出声；
  - 新回复按顺序读完。
- **E（Chromium）**：5 句全部 `ended`，句间空档和基线同一量级（都在 300ms 以内），首音延迟不比基线差。
- **F**：播放中关闭朗读，200ms 内停止出声，提示消失。
- **G**：整个页面生命周期内创建的 audio 元素不超过 2 个（Claude 会拦截 `Audio` 构造函数和 `document.createElement("audio")` 计数）。
- **H**：390 宽和 1280 宽下截图，提示行显示正常；输入区其他部分和基线逐像素一致（提示不出现时）。
