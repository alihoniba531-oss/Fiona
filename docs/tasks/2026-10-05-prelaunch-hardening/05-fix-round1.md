## 1. 必须修复

### F1　GIF 不再一律使用 `disposal=2`

**问题**：动图 GIF 重编码时，每一帧都强制 `disposal=2`。Pillow 因此把每一帧都写成整幅画面，帧间差分全部丢失，体积膨胀几十到上百倍。复核实测：
- 211 KB 的 GIF 变成 16 MB；
- 按规格上限，一个 1 MB 的 GIF 落盘 250 MB。

问题位置在 `media.py:120-124`。

**改法**：
- 只在确实需要擦除的帧上设 `disposal=2`：源图有透明，或者某一帧把上一帧不透明的像素变成了透明。其余帧不传 `disposal`（或者用 1），让 Pillow 自己做帧间差分。
- 现有几组混合 disposal 的透明 GIF「逐帧 RGBA 一致」测试必须继续通过。

**新增回归测试**（放进 `test_upload_metadata.py`）：
- 造一个不透明 GIF：复杂的静态背景（例如量化成 64 色的噪点），上面有一个小块在动，100 帧；
- 广场和聊天两条路径的输出体积都不得超过输入的 2 倍；
- 透明 GIF 的输出体积也要设一个合理上限，比如不超过输入的 3 倍。

## 2. 可优化项（本轮一起修）

1. **上传原件临时文件**（含 GPS）：
   - 进程被强制结束时，`.upload_*` 这类临时原件可能残留在上传目录里。要做三件事：
     - 服务启动时清扫超过 1 小时的上传临时文件；
     - `main.py` 访问 `/uploads/` 时，对点开头的文件一律返回 404（不论是否登录；`.generated_`、`.reference_` 原有的私有判定逻辑保持不变，它们本来也不该被直接读）；
     - `deploy/fiona-backup.sh` 打包上传目录时排除点开头的临时文件。
   - 测试覆盖：启动清扫、对点开头文件返回 404、备份不含临时文件。
2. **在事件循环一侧排队**：
   - 广场路径改为先在事件循环上等一个 `asyncio.Semaphore(2)`，拿到后再派发到线程；排队期间不占默认线程池。
   - 聊天路径：`_save_uploaded_image` 里获取线程信号量时加超时（例如 10 秒）；超时返回 503「服务器繁忙，请稍后再发图片」。
   - 修掉 anyio 取消作用域下 `_process_upload_off_loop` 的忙等：复核实测，取消后事件循环线程空转了 2.4 秒 CPU。可以参照 `chat_service.py` 里现有的做法，只等一次 shield，然后安排清理。
3. **内存**：不改规格定的上限，只做低成本优化：
   - 没有方向标签时跳过 `exif_transpose` 的复制；
   - `convert` 和 `paste` 之后，立即关闭上一份中间图像；
   - 动图逐帧处理时，不要在列表里同时留着两份全尺寸帧。
   - 报告里贴出优化前后，用复核员那几个样本测得的峰值内存。
4. **聊天发图中途取消留下孤儿文件**：
   - 在 `chat_service.py` 调用处，用 `asyncio.shield` 包住 `to_thread` 任务，并加完成回调：调用方被取消后，如果线程最终成功写盘，就删除那个文件。
   - 加测试：在等待线程期间取消，线程完成后上传目录里不留文件。
5. **每日上限的计数点**：`/cards/detail` 和 `/asr/recognize` 在「缺 `DASHSCOPE_API_KEY`」这道本地检查之后才计数（做法同 `/hot/expand`），并补上测试。
6. **前端 429 的区分**（`page.tsx`）：
   - 只有当响应体里带 `retry_after` 字段时（这是每日上限才有的），才显示后端文案；免提路径也只在这种情况下关闭免提。
   - 按 IP 每分钟限流的 429（slowapi 返回的英文 `error`）维持原来的处理方式，不提示、不关免提。
   - 拼接「，免提已关闭」之前，先去掉文案末尾的句号，避免出现「。，」。
7. **透明 PNG**：RGB 或 L 模式、带 `transparency`（tRNS 色键）的图，转成 RGBA 或 LA 再重建，不能丢掉透明。补测试。
