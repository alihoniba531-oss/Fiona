### V1 恢复「讨论不生图」的兜底（第 2 轮引入的回归）

第 2 轮删掉了 `recognize_intent_with_fallback` 里这段：

```python
if intent_result.get("intent") == "generate_image" and image_generation_discussion(message):
    intent_result = {"intent": None}
```

删掉之后，意图模型把能力咨询、否定、教程类问题（如「你会画画吗」「怎么生成图片」「不要画了」）误判为 `generate_image` 时，没有任何兜底，会直接生图并扣费。

要求：

- 补测试：意图模型打桩返回 `generate_image`，消息是上述三类讨论句时，不生图。

### V2 生图画面描述必须用用户的完整原话（纠正规格作者在 M1 中的错误）

M1 里写的「画面描述用模型给出的参数」是规格作者的错误。原代码有意用完整原话，注释写的是「分类器的短 JSON 不能替换或截断用户完整的画面要求」；而且意图模型的 `max_tokens=150`，长描述一定会被截短或改写。

要求：
- 自然语言生图（候选确认路径和普通意图路径）一律用 `ctx.message.strip()` 作为画面描述。意图模型只负责判断「是不是要画图」。
- 比例继续从原文推断（`image_aspect_ratio`）。模型给出合法比例、而原文没有写比例时，可以采用模型给的值。
- 补测试：意图模型打桩返回一个被截短的 prompt 时，送去生图的仍是完整原话。

### V3 意图模型仍会把评论和抱怨判成生图

规格作者用**真实意图模型**跑了复核员的语料：
- 35 句非命令里，有 5 句仍被判为 `generate_image`；
- 17 句正常命令全部正确。

被误判的句型包括：
- 谈论生图价格或扣费的陈述，例如「生成一张图片要十颗草莓」「画一只猫扣了我十颗草莓」；
- 回忆或愿望，例如「画一张全家福是奶奶生前的愿望」；
- 口语反问，例如「画一只猫可以不」「画一只猫哪有那么难」。

要求：
- 在 `INTENT_PROMPT` 里补充「谈论生图这件事本身 → null」的规则与少量示例。覆盖的句型包括：
  - 价格、扣费、耗时、难度的陈述或反问；
  - 对已生成结果的评价或抱怨；
  - 回忆、愿望、第三人称叙述；
  - 口语反问（……可以不 / 哪有那么难 / 不就行了）。
- 示例请**自己另写**，不要照抄上面这些句子；规格作者会用未公开的语料验收。
- 明确的祈使请求（画一只…、帮我生成一张…、能帮我画…吗）必须仍然判为 `generate_image`。
- 不需要真实调用验证（沙箱内不做真实模型调用），由规格作者负责实测。

### V4 Chromium 与 WebView2 的朗读首音延迟变慢

**现状**：Chromium 请求 `<audio>` 时也会带 `Range: bytes=0-`，所以现在同样走「整句非流式合成后返回 206」的路径。实测同一句首字节从约 0.6 秒变成约 1.6 秒。桌面端（WebView2）和 Chrome 的每一句朗读都会晚大约 1 秒，违反原规格「首音延迟不能明显变差」。

**要求**：
- 请求是开放区间且从 0 开始（`Range: bytes=0-`），并且这张票据还没有缓存时，按原来的流式合成返回 **200**（Chromium 和 WebView2 接受）。
- 闭区间请求继续走缓存合成 + 206，例如 WebKit 的 `bytes=0-1`、`bytes=0-N`。
- 已有缓存的票据，任何 Range 请求都读缓存返回 206。
- 补测试覆盖：
  - `bytes=0-` 首次请求是流式 200；
  - `bytes=0-1` 之后接 `bytes=0-N` 是 206，且只合成一次；
  - 不带 Range 的请求是流式 200。
- 在报告里说明这样判定的依据。
