# 规格修订 R1：平台侧改用「生图判断器」

日期：2026-10-10。本修订与 `02-spec.md`、`05-fix-r0.md` 同等效力，冲突处以本修订为准。

## 0. 起因：真实 Key 评测（作者方在沙箱外执行，脚本与日志由作者方保存）

评测条件：
- 用仓库 `services/image_tool.py` 的工具定义，加上真实 `persona.build_agent_prompt` 生成的系统提示；
- 流式请求，参数 `tool_choice="auto"`，关闭思考；
- 5 类正例：直接画、把上面的提示词画出来、改成动漫风、点名千问、作者截图原句；
- 6 类反例：只要提示词、问哪个模型好、评价已有图片、问价格、只是提到画画、问用法。

| 回复模型 | 正例（应调用） | 反例（不应调用） |
|---|---|---|
| 平台主力 `qwen3.8-omni-flash` | 6/10；系统提示加工具规则后 9/15 | 全对 |
| 平台轻量 `qwen3.8-flash` | 8/10；加规则后 12/15 | 全对 |
| DeepSeek `deepseek-v4-pro` | 10/10 | 11/12 |

千问失败时**不是漏调**，而是**假装已经画好**，例如：
- 「画好了，一只圆滚滚的橘猫……」
- 「[这里生成了 1 张图片]」
- 用文字模拟工具调用：「【调用工具】：generate_image」「［调用工具：generate_image（prompt=…）］」

这比现状更糟。

对照实验：把同样的对话交给**单独的判断器调用**（`qwen3.8-flash` 或 `qwen3.8-omni-flash`，JSON 模式，只读最近 6 条对话，提示词见第 2 节）。两个模型的正例、反例各 3 遍，**全部 33/33 正确**：
- 引用上文时原样沿用之前的英文提示词，「改成动漫风」能正确改写；
- 点名千问能选对模型。

## 1. 新的分工：两种模式

`image_tool_on` 的判定条件保持 3.1 节原样（开关、chat 模式、无本轮图片、`crisis_level is None`、非 `byok_unreserved`、无 BYOK 错误），**唯一改动是删除「回复模型在白名单内」这一条**。

`image_tool_on` 为真时，按回复模型分两种模式：

| 模式 | 适用的回复模型 | 由谁决定画不画、画什么 |
|---|---|---|
| **原生工具模式 `native`** | BYOK `anthropic`（三个型号）；BYOK `deepseek`，模型名精确为 `deepseek-v4-pro` 或 `deepseek-flash` | 由回复模型本身通过 `generate_image` 工具调用决定。实现保持 02-spec 原样（4.4 里的 BYOK 部分、4.5、4.6） |
| **判断器模式 `planner`** | 其余全部：平台主力槽与轻量槽、BYOK `dashscope`、`moonshot`、`zhipu`、`custom`，以及 `deepseek` 的其他型号 | 由平台的「生图判断器」决定；**回复模型不下发任何工具** |

**平台 `stream_normal` 不再下发工具**：
- 删除 02-spec 4.4 中「平台回复带工具」的实现（`image_tool` 参数、`max_tokens` 1200、`tool_calls` 累积等），恢复为与 `7ac7b57` 相同的代码；
- 不保留这部分死代码；
- 平台请求参数里永远不出现 `tools`。

## 2. 生图判断器（新增，放在 `backend/services/image_tool.py` 或同目录的新模块）

### 2.1 调用方式

- 模型：平台轻量模型 `qwen3.8-flash`。
- 客户端：复用 `llm.py` 中已有的千问客户端对象，只 import，不修改 `llm.py`。
- 参数：
  - 非流式；
  - `response_format={"type": "json_object"}`；
  - `max_tokens=600`；
  - `extra_body` 与该客户端现有的关闭思考设置一致；
  - 单次总超时 8 秒，不重试；
  - 在线程中执行，不阻塞事件循环。

### 2.2 输入

- system：下面的判断器提示词，逐字使用。
- user：一段文字记录，取 `ctx.history` 最近的消息加上本轮主人原话，**共最多 6 条**。
  - 每条前缀为「主人：」或「你：」；
  - 每条截断到 600 字；
  - 按时间顺序排列，最后一条是主人本轮原话。
  - `ctx.history` 中 assistant 消息的正文包含之前的「使用的描述」行，原样保留。

判断器提示词：

```
你是生图意图判断器。阅读对话（最后一条是主人刚说的话），判断主人这一句是否要求「现在生成一张图片」。
要求生成图片的情形：明确让你画/生成图片/出图/生成照片；让你把之前出现的描述或提示词画出来；让你在之前的描述上修改风格或内容后再画。
不算的情形：只要提示词或文案；讨论、比较、询问生图模型、价格或用法；评价已有图片；只是提到自己画画。
如果要生成，把要画的内容整理成一段完整、具体的画面描述（可沿用之前的英文提示词原文并按要求修改），不得写入账号名、真实姓名或私人细节。
只输出 JSON：{"draw": true或false, "prompt": "画面描述或空串", "model": "seedream-5.0-flash" 或 "qwen-image-3.0" 或 null（仅当主人点名：Seedream/豆包/即梦→seedream-5.0-flash；千问/通义/Qwen→qwen-image-3.0）, "aspect_ratio": "1:1"/"16:9"/"9:16" 或 null}
```

### 2.3 输出校验与结果

- `draw` 必须是布尔值 `true`，并且 `prompt` 去掉首尾空白后非空、不超过 1500 字，才算「要画」。
- `model`、`aspect_ratio` 不在枚举内时，视为未提供。
- 出现以下任一情况，判为**「判断器不可用」**：
  - 超时或其他异常；
  - 返回的不是 JSON；
  - `draw` 不是布尔值。
- 日志和 trace 只记录异常类型和耗时，**不记录对话内容和描述**。

### 2.4 何时调用：预筛

只有本轮主人原话命中下面的**预筛正则**（忽略大小写），或命中现有的 `explicit_image_intent` 时，才调用判断器。没命中时不调用，以免给每轮聊天都增加延迟。

```
画|绘|图|照片|相片|生成|出一张|来一张|风格|.风[。！!？?…～~]?$|提示词|prompt|seedream|即梦|豆包|千问|通义|qwen|draw|image|picture|photo|render|海报|壁纸|插画|头像
```

预筛只用来保证召回，最终由判断器决定画不画。预筛常量与判断器提示词都要写成模块级常量，供测试引用。

## 3. 判断器模式下的路由（替换 02-spec 4.6 中对这种模式的规定；原生模式仍按 4.6 执行）

在计算 `image_tool_on` 的位置（高危分支、面板模式、「缺少修图参考」引导之后，自然语言生图候选之前），如果 `image_tool_on` 为真且模式为 `planner`：

**1. 预筛命中时**，调用判断器：

- **判断器不可用**：本轮按 `image_tool_on` 为假处理，旧路由逐字节原样执行。trace 记 `image_planner = "error"`。
- **要画**：
  1. 如有 `generate_image` pending，清除；
  2. 不调用 `detect_mode`，不调用回复模型，也不调用意图识别；
  3. 直接调用 4.3 的生图执行核心，参数为：`prompt` 取判断器结果；`model_id` 按「判断器给的 model → `TOOL_DEFAULT_IMAGE_MODEL`（Seedream）→ 降级」顺序选择；`aspect_ratio` 取判断器结果；`lead_text=""`；`source="tool"`；
  4. trace 记 `image_planner = "draw"`、`image_source = "planner"`；
  5. 事件、落库、计费、错误文案全部按 4.3（不发 `reply_model`，因为这一轮没有调用回复模型）；
  6. 结束本轮。
- **不画**：trace 记 `image_planner = "no"`，按下面第 2 条继续。

**2. 继续路由**（预筛没命中，或判断器判为不画）：

- 跳过自然语言生图候选块，因为判断器已经做出裁决；预筛没命中时，候选也不可能命中。
- 遗留的 `generate_image` pending：取消短语照旧取消，其他情况清除后继续。
- 不新建 `generate_image` pending。
- `detect_mode`、镜子模式、天气 pending 及其他工具的意图路由照旧。
- 意图识别返回 `generate_image` 时，视为无意图；意图识别抛异常时，也视为无意图。
- 普通回复（平台 `stream_normal` 或 BYOK `_stream_byok_reply`）**不带工具**。

**判断器模式的好处**：
- 镜子模式下也能识别生图请求，因为判断器在 `detect_mode` 之前运行；
- 回复模型不会也不能假装画图；
- Kimi、智谱、自定义地址的用户也能用上下文生图。

## 4. 对 02-spec 其他条款的影响

- **4.3 执行核心**：两种模式共用。判断器模式下 `lead_text` 为空，所以不会在正文前多出空行。
- **4.5 BYOK**：只对原生模式下发工具。`dashscope`、`moonshot`、`zhipu`、`custom` 一律不传 `tools`。BYOK 判断器模式下的生图在 `_stream_byok_reply` 之外执行，不调用用户模型，也不计 `byok_chat`；BYOK 文字回复照旧免费，图成功扣 10 颗。
- **4.7 persona**：保持本轮已做的修改；原生模式与判断器模式都适用。
- **4.8 前端**：不变。
- **4.9 文档**：改写为两种模式。必须写明：
  - 判断器使用的模型；
  - 判断器读取最近 6 条对话（每条最多 600 字），发送给阿里云 DashScope；
  - 预筛命中时这一轮会多一次约 1–5 秒的判断器调用；
  - 判断器不可用时退回旧路由；
  - 已知局限更新：判断器模式下镜子模式也能生图；Kimi、智谱、自定义地址改走判断器模式，不再退回旧路由。
- **4.10 测试**：平台路径相关的用例改为判断器模式。至少覆盖以下几点：
  - 预筛命中、未命中，以及未命中时不调用判断器；
  - 判断器结果分别为要画、不画、不可用（超时、非 JSON、`draw` 不是布尔值、`prompt` 为空、`prompt` 超长）；
  - 判断器给出 model 与 aspect_ratio 时被采用；
  - 「要画」时：不调用回复模型、不调用意图识别、不调用 `detect_mode`；
  - 镜子模式下仍能生图；
  - 平台请求参数里永远没有 `tools`；
  - BYOK `dashscope`、`custom` 走判断器且不传 `tools`；
  - 判断器的输入文字记录最多 6 条、每条最多 600 字，且最后一条是本轮原话；
  - trace 和日志中不出现对话内容或描述。
- **验收 5.4b**：打开开关跑全量时，必须用一个**不放在 `backend/tests/` 下**的 pytest 插件（通过 `-p` 加载，放在任务目录或临时目录），把判断器打桩为固定返回「不画」，并禁止真实网络请求。之后列出全部失败用例及逐条原因，要求同 02-spec。其他验收标准不变。

## 5. 不变的部分

原生模式（BYOK Claude、DeepSeek 两个型号）的全部实现，以及 02-spec 中其余约束、受保护文件、测试纪律、第 6 节停下来的条件，全部不变。
