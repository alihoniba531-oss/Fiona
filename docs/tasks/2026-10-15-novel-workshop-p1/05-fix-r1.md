## 必须修复

### F1【资金】草莓预扣必须是单个原子事务（billing.py）

**问题**：现在的 `reserve()` 拆成了两个事务：先「扣用户余额」，再「写 `novels.reserved_strawberries` 和 `novel_steps` 的 reserved 行」。aiosqlite 在任务被取消时，已经发出的 commit 仍会完成。复核员 A 用探针证实了三个丢账窗口（用户多付、平台少收、崩溃后丢账）；在混沌测试里，账目守恒 20 次中有 19 次被打破，用户最多多付 85 颗草莓。

**修法**：
- 在**同一个连接、同一个 `BEGIN IMMEDIATE` 事务**里依次完成三件事：
  1. 执行与 `database.reserve_strawberries` 相同的每日补给逻辑；
  2. 按条件扣减用户余额；
  3. 写入 `novels.reserved_strawberries` 和 `novel_steps` 的预扣记录（`billing_status=reserved`）。

  任何一步失败，整个事务回滚。
- **不得修改 `database.reserve_strawberries` 本身的行为**。需要复用补给逻辑时，抽出一个不改变外部行为的内部函数，或者在 billing 里实现等价的 SQL；采用后者时，要有测试证明两者的补给结果一致。
- 退款和结算同样必须是单事务：用户余额、`novels` 计数和 `novel_steps.billing_status` 三处一起改。
- 提交阶段要防取消：用 `asyncio.shield`，或者等价的「提交完成之前不响应取消」写法，保证不会出现「已经提交但调用方以为失败」的情况。
- **测试**：把复核员 A 的混沌守恒探针改写成正式测试，放进 `tests/test_novel_p1_*.py`。场景是 critique 并行、随机暂停或取消、网络失败、坏 JSON、缺 usage 混在一起，至少跑 3 个固定随机种子，每个种子 20 次。每次都要断言：**用户余额减少量 == 该书 spent**，且所有书 reserved 归零后，总账守恒。

### F2【资金】结算与「步骤成功」必须同事务，或者结算要幂等（billing.py、store_db.py、llm_router）

**问题**：现在结算和 `write_step(ok)` 分在两个事务里。如果取消恰好落在两者之间，续跑时同一次成功的调用会被计费两次。

**修法**：二选一。
- 把结算和步骤 ok 写入合并成一个事务；
- 或者给结算加幂等键（`novel_id + step_key + attempt`），重复结算时直接跳过。

**测试**：在结算之后、写入 ok 之前注入取消，然后续跑。断言该调用只计费一次，余额守恒。

### F3 改最新一章与后台写作的竞态（service.py / runner.py）

**问题**：`edit_chapter` 先判断「这是不是最新一章」，然后才取消后台任务。如果在这两步之间 worker 提交了第 N+1 章，正典圣经就会丢掉第 N+1 章的归档。复核员 A 已经复现。

**修法**：
1. 先取消并等待后台任务确实停下；
2. 然后在数据库事务里重新判断哪一章是最新一章；
3. 再执行改稿流程。

改稿期间，这本书不得被 resume 或 continue 重新拉起；需要的话给书加一个「改稿中」的锁标记。

**测试**：构造 worker 正好提交第 N+1 章的时序，断言改第 N 章时按「更早的章节」规则处理，也就是把第 N+1 章标为 stale，而第 N+1 章的归档不丢。

### F4 改早期章节导致待批细纲 500（service.py）

**问题**：修改早期章节时，会把处于 `awaiting_plan_approval` 的待批细纲行也标成 stale，之后调用 approve 或 redo 就会返回 500。

**修法**：标 stale 时跳过还没写成正文的待批细纲行（status 为 planning 或 awaiting_plan_approval）。approve 和 redo 遇到状态不对的行时，返回 409 并附中文原因，不能返回 500。

**测试**：重现上述流程，断言修复后不再出现 500。

### F5 上下文压缩漏了两处（context.py）

**问题**：复核员 A 发现，除了卷摘要以外，还有两处会随章数持续增长：锁定区里的**新增配角卡片**从来不裁剪，人物状态里的 **knows 列表**没有上限。

**修法**：
- **配角卡片**：简报、写手上下文包、审校输入和档案员输入里，锁定区人物只放以下三类：
  - 全部主要人物；
  - 最近 3 章出场过的配角；
  - 本章细纲点名的配角。

  其余配角的卡片不下发（圣经里照常保存）。档案员校验人物 ID 时，仍以完整人物表为准，避免因为裁剪而误判「人物不存在」。
- **knows 列表**：每个人物最多下发最近 30 条，圣经里照常保存全部。
- **测试**：用 60 章规模的样例，在 open 伏笔数量固定的前提下，断言第 30 章和第 60 章的输入字符数相差不超过 10%。open 伏笔数量本身的增长不计入这项断言。

### F6 自带模型运行中失效时，应暂停而不是失败（runner.py、byok_bridge.py）

**问题**（复核员 B 的 M1）：用户在书运行期间停用或删除了自带模型，书会进入 `failed` 状态，无法恢复，也没有记录原因。

**修法**：
- 新增 `pause_reason=byok_unavailable`，书转为 paused，并保存中文原因。
- 用户重新启用自带模型后，或者把对应角色改成平台模型后，可以 resume。如果需要支持「改角色模型」，就在 `PATCH /novels/{id}` 里允许修改 `agents`；修改时同样按第 8 节校验，并且只允许在 paused 或 awaiting_* 状态下改。

**测试**：运行中停用自带模型，书转为 `paused/byok_unavailable`；重新启用后 resume 能继续写下去。

### F7 不支持的自带模型要给出明确文案（byok_bridge.py、service.py）

**问题**（复核员 B 的 M2）：规格要求的「该模型暂不支持用于小说工坊」被折叠成了笼统的「请先启用支持的自带模型」。

**修法**：区分以下三种情况，各给对应的中文文案：
- 没有启用自带模型；
- 自带模型的厂商不被支持（custom、moonshot、zhipu）；
- 厂商支持，但具体型号不在已知型号表中——这种情况给出「该模型暂不支持用于小说工坊」。

建书时返回 422，运行中按 F6 暂停。

**测试**：三种情况的文案各断言一次。
