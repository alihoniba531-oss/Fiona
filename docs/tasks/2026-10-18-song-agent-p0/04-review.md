## 4. 可优化项（不阻断交付）

1. **终态与退款之间的对账缺口**：所有失败路径都是「先提交终态标记，再调 `refund_version`」两个事务（规格参考设计即如此）。若进程恰在两步之间崩溃、或退款事务遇 DB 锁超时抛错（后台任务里被吞），版本会停在 `failed/rejected/uncertain/expired + billing_state='reserved'`，而 `recover_on_startup` 只扫 `submitting`，这笔预扣将永久无人退还。建议：启动恢复时追加一条对账——`status IN ('failed','rejected','uncertain','expired') AND billing_state='reserved'` 的版本逐个 `refund_version`（该函数本身幂等，重复调用无害）。
2. **报告 §⑤.2 对镜子模式的陈述与代码不符**：`state.sys_prompt_final` 在镜子分支之前赋值（`claude_agent.py:414–419`），而 `stream_mirror`/`_stream_byok_reply` 都使用 `sys_prompt_final`（`chat_service.py:1187`、`:384`），因此智能体模式下的镜子轮系统提示**会**包含写歌提示词（无工具、无计费影响，安全规则仍在末尾）。规格未明确排除镜子轮，行为可接受，但报告「镜子模式不追加写歌提示词」的说法应更正，或在代码里对镜子轮排除。
3. **`poll_once` 对非 `PollError` 异常不推迟**：`provider.query` 抛出意外异常（实现 bug 类）会逃到 `run_poller` 的 `except`，该版本 `next_poll_at` 未更新，下一轮 5 秒后立即重试同一版本，可能形成热循环刷日志（查询免费，无资损）。建议在 `poll_once` 内对单版本处理加兜底 try，异常时同样 `_postpone_version(+10s)`。
4. **写歌工具写路径无 users 存在检查**：删号事务与进行中聊天轮并发时，`song_save_brief`/`song_save_lyrics` 可能在删号提交后新建孤儿行。用户名会进 `retired_usernames` 永不复用，孤儿行无人可达、无隐私影响，且规格只要求轮询/下载写库带 EXISTS 守卫（已实现）。建议 P1 顺手在 `create_project`/`save_lyrics` 事务内加 `EXISTS(SELECT 1 FROM users …)`，或启动对账时清理 owner 不存在的 `song_*` 行（当前 `cleanup_orphans` 只清文件不清 DB 行）。
5. **押韵标记语义可更精确**：XAXA 的奇数行保持 `rhyme_ok=null`（前端不显示标记）；AAAA 任一行不同辙时全部行标 `false`（前端把实际同辙的行也显示「不押」）。均为规格模糊处的合理解释，仅影响展示精度。
6. **`npm run build` 无法在符号链接 node_modules 的副本里执行**（Turbopack 硬限制）：今后给复核方的副本建议用真实目录或 `--webpack` 兼容路径，否则复核侧只能验证 lint/tsc。
7. **同幂等键并发双 POST 的理论窗口**：`BEGIN IMMEDIATE` 已使写事务串行化，正常不会撞 `UNIQUE(owner,idempotency_key)`；万一发生（如未来改连接模式），第二个请求会以 IntegrityError→500 结束而非返回首版，无资损。可在路由层把 IntegrityError 归一成「返回已存在版本」。
