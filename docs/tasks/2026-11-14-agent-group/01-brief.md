# 多智能体讨论群：简报与方案草案

日期 2026-11-14，基线 `859e2c5`，分支 `feat/agent-group`。等级 L3：规格须作者确认后才派单。

## 1. 作者的诉求（原话）

> 我现在需要在 Fiona 上面增加另外一个功能：多智能体讨论群功能。用户提出诉求，多智能体进行多维度调研干活，直到干到完成任务为止

> 另外需要与分身模型可以进行交互

## 2. 作者已定的方向（2026-11-14）

1. 干什么活：调研并交付成果文档（带来源的报告、方案、对比表）。不写代码，不操作外部账号，第一期不调用 Fiona 的生图、写歌、书斋、短片。
2. 成员阵容：主持人按任务点将。平台备角色池，主持人按诉求挑 3–5 个并说明分工，开工前作者可增减。
3. 收尾：开工前对齐完成标准；专设验收角色逐条核对，不过就返工；草莓预算或轮数到上限时停下问是否追加；中途可插话、喊停。
4. 入口：侧栏新增一个书签，点开是群列表和群聊页。
5. 与分身交互，四种都要：分身能看群的进展和成果；分身能替作者发起讨论群（出任务卡，点卡片确认后才开工扣费）；分身能把作者的意见带进群（出意见卡，点按钮后作为插话送进群）；分身作为成员进群发言（带人设和私有记忆，代表作者的偏好）。
6. 分身交互的可用范围与书斋一致：查看进展和成果在平台模型与自带 Claude 的分身上都可用；出卡片的操作只在自带 Claude 的分身上可用。

## 3. 现状事实（详见 `01-investigation.md`）

- 没有现成的群聊。「分身交流」是固定两方、不能插话、明确不带工具的后台任务，表结构写死两方，且被工作室依赖，不能改造成群。
- 书斋的底座可以直接用：`novel.llm_router.LLMRouter`（多厂商非流式调用、同一步骤键命中缓存、网络重试一次、校验失败修正一次）、`ByokBridge`（自带模型）、`FakeLLM`（离线测试）。计费、步骤存储、后台任务器的 SQL 写死了书斋的表，只能照着写一套。
- 联网搜索现成：`tools.native_search.grounded_search`，来源只取搜索接口返回的结果，模型自己写的网址不会进入来源。它是同步函数，与聊天无耦合。
- 平台模型在代码里从未用过原生工具调用。智能体「去搜索」只能做成两步：先让它输出要查的问题，代码去查，再把结果交给它写笔记。
- 后台长任务一律是写库加前端轮询，没有流式推送。
- 侧栏六个静态书签被两条测试锁死；工作室书签是通过准入检查后动态追加的，这条路改动最小。
- 聊天侧已有与书斋互通的两条通道（平台意图与自带 Claude 的工具），任务卡、意见卡可以照书斋草稿卡、修改意见卡的做法。

## 4. 方案草案

### 4.1 一次任务怎么走

讨论不是自由聊天，而是由代码控制的结构化流程，展示成群聊。依据是书斋的两轮盲读：「人人提案再均分合并」输给了「主持人出方案、其他人挑错、主持人定稿」。

1. 立项。作者写下诉求，可贴补充材料，选预算上限。主持人读完后给出：任务标题、目标复述、成果形式与提纲、3–6 条完成标准、点将名单与每人的分工、最多 3 个想问作者的问题。分身（如果在群里）先根据私有记忆补充作者的背景与偏好，答得上的问题直接答。
2. 等作者开工。作者可以改完成标准、增减成员、改分工、换模型、调预算，回答主持人的问题，然后点「开工」。从这一步起才是主要花费。
3. 每一轮：
   - 调研：被派到任务的调研成员各自列出要查的问题（每人最多 3 个），代码联网搜索，成员据搜索结果写调研笔记，每个要点都带来源编号。成员之间并行。
   - 质疑：反方质疑读完本轮笔记，指出证据不足、互相矛盾、遗漏和偏见。
   - 裁决：主持人逐条回应质疑和作者的插话，决定是再查一轮还是开始撰稿。
   - 撰稿：撰稿人写出成果文档，引用来源编号。
   - 分身看稿：分身从作者的角度说这份成果合不合意。
   - 验收：验收人逐条核对完成标准，并检查引用。全部通过即完成。
   - 没通过：主持人安排返工（补查什么、改写什么），进入下一轮。
4. 停下来的几种情况：验收通过；到达轮数上限；到达预算上限；草莓不足；作者喊停。除了验收通过，其余都停下来等作者决定：追加后继续、接受当前成果、或结束。
5. 完成之后作者仍可以提意见并点「按意见返工」，再跑一轮。

### 4.2 成员

- 固定席位：主持人、撰稿人、验收人。
- 点将名额 3–5 个：反方质疑必在其中（保护席位），其余由主持人从调研角色里挑：市场与行业、用户与需求、竞品与对标、技术与可行性、成本与财务、政策与合规、数据与事实核查、综合调研。
- 分身：可选成员，开工前可以移出。它用作者的分身设定和私有记忆发言，只在两个固定位置开口（立项时补充背景、每轮看稿），不参与调研。
- 模型：每个成员一个模型，开工前可改。平台模型按用量扣草莓，选「我的模型」（自带 Key）不扣。默认搭配待试跑后定。

### 4.3 作者怎么参与

- 实时旁观：群聊页每几秒刷新一次，成员的发言一条一条出现（整条出现，不是逐字）。
- 插话：随时在群里说一句，主持人在下一个裁决点读到并且必须逐条回应。
- 喊停、继续、追加预算或轮数、接受成果、结束、删除。

### 4.4 来源与成果

- 每个群有一份来源登记表，来源编号由代码分配。成员只能引用登记表里的编号；成果里的网址全部来自搜索接口，不来自模型。
- 成果是 Markdown 文档，可以含表格，可导出，文末附来源清单。
- 第一期的智能体只看搜索摘要，不逐页精读原文，也不读 PDF。是否加「精读网页」等试跑后再定。

### 4.5 预算与计费

- 建群时定预算上限（草莓）。每次模型调用先预扣、按真实用量结算、失败退还，与书斋同一套做法。到上限就停下来问作者。
- 联网搜索按次收固定草莓数。
- 另有三道闸：每人同时只能有一个群在跑；全站同时在跑的群数上限；每人每天新建群数上限。

### 4.6 开关与范围

内测期间默认关闭，开关加白名单才开放（同书斋）。书签只对开放的账号显示（同工作室）。

### 4.7 数据与隐私

- 诉求、补充材料、成员发言会发给各成员所用模型的厂商（阿里云百炼、DeepSeek、火山方舟，或作者自带的厂商）。搜索问题和任务目标会发给阿里云百炼。
- 分身进群时，分身设定和私有长期记忆发给分身所用模型的厂商；分身说出的话会进入群聊上下文，被其他成员的模型厂商看到。分身的提示词要求它只说与任务有关的偏好和背景，不复述与任务无关的个人信息。
- 网页与搜索内容一律当数据，不当指令。
- 诉求和插话先过现有的危机规则，命中明确危机信号时不建群，返回求助资源。

### 4.8 分期

1. 第一期：后端引擎。新模块、数据表、流程、计费、接口、离线测试。分身作为成员在这一期。
2. 第二期：界面。书签、抽屉、群列表、新建、群聊页、成果与来源面板。
3. 第三期：分身聊天互通。查看进展与成果（两条通道）、任务卡、意见卡。

每一期各自走规格、派单、门禁、复核。

## 5. 风险与待定

- 多智能体是否真的比单个模型查得更好，还没有证据。书斋当年靠离线小样和盲读才定下流程，这里同样需要先试跑。
- 平台搜索返回的内容够不够支撑一份像样的报告，要看真实返回。
- 每轮的 token 用量与草莓花费现在只有估算（每轮约 150–250 颗），预算默认值要按试跑实测定。
- 侧栏第七个书签在手机底栏放不下，第一期拟只在桌面显示（同工作室）。
- 书签名字拟直接用「讨论群」。

## 6. 试跑计划（规格定稿前）

写一个不进产品代码的试跑脚本，用真实模型把 4.1 的流程完整跑一遍：主持人立项、三名调研成员查资料写笔记、反方质疑、主持人裁决、撰稿、验收。产出完整的讨论记录、成果文档、每一步的 token 用量与折算草莓。用它来回答第 5 节的前三个问题，并把验证过的提示词写进规格。花费须先向作者报价。
