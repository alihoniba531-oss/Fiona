## 1. 产品定义与第一条闭环

Fiona 的核心对象从“陪伴用户的 Chloe”扩展为“属于每个用户的数字身份”。分身有名字、形象、表达方式、记忆和能力；用户决定它对外展示什么、何时交流、能使用哪些能力。

建议第一版每个账号一个主要分身，数据模型允许未来扩展多个。现有 Chloe 保留为初始人格模板，已有用户的私有历史继续归属于本人。

第一条可验证的体验：

> 用户 A 创建分身，安装“旅行规划”Skill；用户 B 创建分身并允许交流。双方围绕一次旅行展开分身对话，A 的分身调用 Skill 生成方案，双方可以查看过程并随时停止。Skill 作者发布新版本，用户可以查看版本差异并选择更新。付费阶段增加购买、授权与作者收益记录。

这里需要明确三个不同对象：

- **用户账号**：拥有分身、购买授权、承担调用费用并接收作者收益。
- **AI 分身**：承载人格与交流身份，按主人授权使用能力。
- **Skill**：有版本、输入输出、执行方式和权限的能力包。购买获得使用许可，再将许可安装到分身。

建议首期交易指“作者出售使用许可”。购买者转售 Skill、分身自主花钱、作者代运营分身属于另外的产品规则，暂不纳入首期。

| 对象 | 关键关系与职责 |
| --- | --- |
| `agents` | 所属账号、名字、头像、人格配置、公开状态、声音配置 |
| `agent_memories` | 所属账号与分身、内容来源、可见范围、删除状态 |
| `conversations` | 类型、创建者、状态、主题、轮数和预算上限 |

会话内存状态也需要一起改造：当前待补全工具参数、模式和历史以用户名定位，未来至少按“账号 + 分身 + 会话”隔离。

旧数据迁移应为每位用户创建默认分身和一个私有历史会话，再回填旧消息。旧画像不自动变成公开名片；不能从前端“新对话”的时间筛选反推历史上不存在的会话边界。迁移应有版本记录、备份、回填校验和兼容旧客户端的过渡入口。

数据库选型不妨碍先验证分身模型。当前 SQLite 可以继续用于受控原型；进入多人并发和付费交易前，需要验证事务、迁移和恢复流程，并决定是否迁移 PostgreSQL。当前项目没有现成的 PostgreSQL 实现。

## 5. 分身交流如何运行

分身间的交流需要服务端调度，不能依赖两个浏览器互相触发回复。

1. 用户指定主题和自己的分身，对方按公开接待设置或单次邀请授权参与。
2. 服务端创建会话，固定参与者、轮数和费用承担方式。首期可采用“最多六次分身回复”的可调整默认值，并同时设置硬性用量上限。
3. 每次生成前检查参与权限、是否已停止、剩余预算和当前发言者，再准备该分身允许使用的上下文。
4. 生成一条消息或执行一次已授权 Skill，记录结果与用量，然后决定是否继续下一轮。
5. 结束、失败或用户停止后保存状态和总结。进程重启不能重复发言或重复触发收费动作。

公开人格、主人私聊、对外会话和 Skill 可读资料应分开管理。分身对外发言默认只使用公开名片、当前会话以及主人明确允许分享的资料；不能把主人的全部聊天历史放入对外模型上下文。

首期自动交流中仅允许低副作用能力。涉及发消息给第三方、购买或发布内容的动作需要独立授权机制。谁发言、代表哪个账号、调用了什么能力，应在消息与运行记录中可见。

## 6. Skill 的最小产品形态

建议先支持两种受平台控制的能力：提示词/工作流配置，以及对现有官方工具的封装。一个可发布版本至少包含：

- 名称、作者、用途、版本号与更新说明。
- 输入和输出定义、使用示例、运行测试样例。
- 所需模型能力、允许调用的工具与数据范围。
- 执行超时、用量限制、兼容条件与费用说明。
- 完整性校验信息和审核状态。

运行路径为：`用户请求 → 会话与分身权限 → 使用许可 → 已安装版本 → 输入校验 → 执行 → 结果与用量记录`。

当前 `execute_intent` 可逐步封装为官方适配器，但工具选择必须受服务端白名单和参数校验约束。第一版不接受任意第三方 Python/Shell 代码直接在 API 进程执行；如果以后支持代码包，需要独立执行环境、资源限额和受控网络访问。

Skill 包里的文字是能力内容，不能修改平台权限。运行时只提供本次任务必要的数据和短期凭据，不将平台密钥或主人完整记忆交给作者。

建议以现有联网搜索、旅行规划、网页摘要作为首批官方 Skill。首期提供手动选择调用以保证可测试，再增加在已安装集合内的自动选择。卸载/停用后禁止新调用；更新固定到新版本，新增权限需要重新授权。

## 7. 交易闭环

先验证免费安装和真实执行，再接入付费使用许可。付费版本需要明确“一次性购买的版本范围”与“后续模型运行费用”，商品价格不能让用户误以为包含无限调用。

基本流程：`浏览 → 服务端报价 → 创建订单 → 支付 → 验证回调 → 发放许可 → 安装 → 使用 → 作者收益记录`。

交易必须由服务端确认金额、币种、商品和版本；不能根据浏览器显示的“支付成功”授予使用权。同一个支付事件只能处理一次，确认付款、记录收入和发放许可应能原子完成或可靠重试，避免重复授权、重复结算与付费后无许可。

退款、支付失败、版本下架和退款后的许可撤销要有明确状态。作者收益应区分待结算、可结算与已结算；现有草莓余额和进程内预算不能替代这些记录。实际支付渠道、币种、抽成和结算周期在接入支付前确定。

## 8. 推荐实施顺序与验收

| 阶段 | 实施内容 | 验收要求 |
| --- | --- | --- |
| M1：分身基础 | 分身 CRUD、公开名片、独立会话与私有记忆；旧数据迁移 | 两个测试账号分别创建分身，跨账号不可读私聊；刷新/切换会话不串历史 |
| M2：分身交流 | 参与授权、有限轮次调度、停止、记录与总结 | 两个分身完成一次有主题交流；撤销授权与耗尽预算后停止继续执行 |
| M3：能力市场 | 三个官方 Skill、版本、免费许可、安装/卸载、运行记录、受控创作者发布 | 安装后实际调用；未授权或卸载后无法调用；作者发布版本能被用户获取 |
